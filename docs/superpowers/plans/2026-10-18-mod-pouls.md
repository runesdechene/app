# Mod « pouls » — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** afficher les six chiffres du pouls du Hub dans un panneau Claude Code, sur les deux machines d'Uriel, sans poser de clé puissante sur aucune d'elles.

**Architecture:** une migration sort de `hub_ouverture` le calcul des bornes de période et le compteur `actifs`, pour que deux appelants s'en servent sans duplication ; une Edge Function `pouls` protégée par un secret d'en-tête appelle ce helper avec la clé `service_role` et ne renvoie que le pouls ; un mod Claude Code appelle cette fonction en HTTP et dessine le panneau.

**Tech Stack:** PostgreSQL (plpgsql, Supabase), Deno (Edge Functions, `deno test`), TypeScript strict + JSX du moteur de mods (`claude plugin test`).

**Spec:** `docs/superpowers/specs/2026-10-18-mod-pouls-claude-code-design.md`

## Global Constraints

- TS strict partout : pas de `any`, pas de `@ts-ignore`, pas de `as unknown as`.
- Conventional Commits, un commit par tâche qui marche.
- Migration numérotée **528** (la dernière du dépôt est `527_hub_comptes_par_provenance.sql`), `-- WHY:` en tête, canal unique `npx supabase db push --linked`, **appliquée par Uriel**.
- Tout `CREATE OR REPLACE` part de la **définition live** copiée entière. Les migrations 522 à 527 ne touchent ni `hub_ouverture` ni `_hub_pouls` : le fichier de référence est `521_hub_boutique.sql`, à confirmer contre le live avant d'écrire.
- Les six libellés, dans l'ordre : Nouveaux comptes, Comptes réactivés, Actifs, Lieux ajoutés, Visites sur place, Énigmes percées.
- Les quatre périodes, telles que la base les nomme : `jour`, `semaine`, `mois`, `toujours`.
- Le secret ne descend jamais dans un fichier du dépôt : il vit dans `public.app_settings` côté base et dans les options du plugin côté poste.

## Review Focus

Cinq façons dont ce logiciel peut blesser quelqu'un qui s'en sert, et le test qui les épingle :

1. **Période inconnue** envoyée à la fonction (un mod d'une version plus récente) → refus net, pas une erreur 500 ni un corps vide. *(Tâche 2)*
2. **Secret absent ou faux** → refus, et aucun chiffre ni message d'erreur de la base dans la réponse. *(Tâche 2)*
3. **Base injoignable ou RPC en erreur** → le panneau garde les derniers chiffres et les date ; il n'affiche jamais des zéros. *(Tâche 4)*
4. **« Depuis toujours »** → `avant` est `null` : aucune tuile ne doit afficher « 0 % » ou « −0 ». *(Tâche 4)*
5. **Secret jamais saisi** sur une machine fraîchement installée → le panneau s'affiche et dit quoi faire, il n'est ni vide ni muet. *(Tâche 4)*

### Tâche 1 : le SQL — sortir les bornes et `actifs` de `hub_ouverture`

**Files:**
- Create: `supabase/migrations/528_pouls_poste.sql`

**Interfaces:**
- Consumes: `public._hub_pouls(timestamptz, timestamptz) RETURNS jsonb` (mig 506), `public._refus(text, text)`, `public._is_admin()`.
- Produces:
  - `public._hub_bornes(p_periode text) RETURNS TABLE(debut timestamptz, avant_debut timestamptz, avant_fin timestamptz)` — `avant_debut`/`avant_fin` sont `NULL` pour `'toujours'` ; appelle `_refus('Période inconnue', 'periode')` sur une période hors des quatre.
  - `public._hub_pouls_periode(p_periode text) RETURNS jsonb` — `{"pouls": {…six clés…}, "avant": {…cinq clés…} | null}`, `GRANT EXECUTE … TO service_role`.
  - `public.hub_ouverture(p_periode text)` — **signature et sortie inchangées**.

- [ ] **Step 1: Récupérer la définition live**

Demander à Uriel, ou lire avec l'accès prod : `SELECT pg_get_functiondef('public.hub_ouverture(text)'::regprocedure);`
Comparer au corps de `521_hub_boutique.sql`. S'il diffère, **c'est le live qui part dans la migration**, et la différence est signalée à Uriel avant d'aller plus loin.

- [ ] **Step 2: Écrire la migration**

Trois objets, dans cet ordre, avec `-- WHY:` et une ligne `-- SCHEMA CHECKED (18/10/2026, live)` en tête :

1. `_hub_bornes` — le `CASE` sur `p_periode`, `date_trunc` à `'Europe/Paris'` et le recul (`1 day` / `7 days` / `1 month`), repris mot pour mot de `hub_ouverture` ; `debut := '-infinity'` et les deux bornes d'avant à `NULL` pour `'toujours'`.
2. `_hub_pouls_periode` — `_hub_pouls(debut, now())` enrichi de `'actifs'` (`SELECT count(*) FROM users WHERE last_login_at >= debut`), et `avant` par `_hub_pouls(avant_debut, avant_fin)` ou `NULL`.
3. `hub_ouverture` — le corps live, où le calcul des bornes et les clés `pouls`/`avant` sont remplacés par ces deux appels. **Le contrôle `_is_admin()` reste la première ligne**, `attente` et `sante` ne bougent pas.

Grants, en fin de fichier :

```sql
REVOKE ALL ON FUNCTION public._hub_bornes(text) FROM PUBLIC, anon, authenticated;
REVOKE ALL ON FUNCTION public._hub_pouls_periode(text) FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION public._hub_pouls_periode(text) TO service_role;
REVOKE ALL ON FUNCTION public.hub_ouverture(text) FROM PUBLIC, anon;
GRANT EXECUTE ON FUNCTION public.hub_ouverture(text) TO authenticated;
```

- [ ] **Step 3: Vérifier que le Hub ne bouge pas**

Il n'y a pas de banc d'essai SQL dans ce dépôt : la vérification est une comparaison avant/après, faite par Uriel au moment d'appliquer. Noter dans le message de commit la requête à passer :
`SELECT hub_ouverture('semaine');` — la sortie doit être identique à celle d'avant la migration, clé pour clé.


### Tâche 2 : l'Edge Function `pouls`

**Files:**
- Create: `supabase/functions/pouls/index.ts`, `supabase/functions/pouls/reponse.ts`, `supabase/functions/pouls/reponse.test.ts`
- Modify: `supabase/config.toml`

**Interfaces:**
- Consumes: `_hub_pouls_periode(p_periode text)` (tâche 1) ; `app_settings(key, value)` lue avec `SUPABASE_SERVICE_ROLE_KEY`, comme `send-push/index.ts`.
- Produces: `POST /functions/v1/pouls`, en-tête `X-Pouls-Secret`, corps `{"periode": "jour"|"semaine"|"mois"|"toujours"}`, réponse `200 {"periode": string, "pouls": {nouveaux, reactives, actifs, lieux, visites, enigmes}, "avant": {nouveaux, reactives, lieux, visites, enigmes} | null, "lu_a": string}` ; `400 {"erreur": "periode"}` ; `401 {"erreur": "secret"}` ; `503 {"erreur": "base"}`.
- Produces (fonctions pures de `reponse.ts`) :
  - `type Periode = 'jour' | 'semaine' | 'mois' | 'toujours'`
  - `type Pouls = { nouveaux: number; reactives: number; actifs: number; lieux: number; visites: number; enigmes: number }`
  - `type Avant = Omit<Pouls, 'actifs'>`
  - `periodeValide(x: unknown): x is Periode`
  - `secretValide(entrant: string | null, attendu: string): boolean`
  - `miseEnForme(periode: Periode, brut: unknown, lu_a: string): { periode: Periode; pouls: Pouls; avant: Avant | null; lu_a: string }`

- [ ] **Step 1: Écrire les tests qui échouent**

```ts
// supabase/functions/pouls/reponse.test.ts
Deno.test('les quatre périodes passent, le reste est refusé', () => {
  for (const p of ['jour', 'semaine', 'mois', 'toujours']) assertEquals(periodeValide(p), true)
  for (const p of ['annee', '', null, 7]) assertEquals(periodeValide(p), false)
})

Deno.test('toujours : avant reste null', () => {
  const r = miseEnForme('toujours', { pouls: { nouveaux: 3, reactives: 34, actifs: 48, lieux: 6, visites: 5, enigmes: 89 }, avant: null }, '2026-10-18T09:00:00Z')
  assertEquals(r.avant, null)
  assertEquals(r.pouls.actifs, 48)
})

Deno.test('un jsonb sans la clé pouls est une erreur, pas un objet vide', () => {
  assertThrows(() => miseEnForme('semaine', {}, '2026-10-18T09:00:00Z'))
})

Deno.test('un secret absent, vide ou faux est refusé', () => {
  assertEquals(secretValide('bon', 'bon'), true)
  assertEquals(secretValide('mauvais', 'bon'), false)
  assertEquals(secretValide('', 'bon'), false)
  assertEquals(secretValide(null, 'bon'), false)
})
```

5. couper le réseau une minute : les chiffres restent, datés, avec la raison nommée.
6. fermer le volet à la main (croix ou `ctrl+x x`) : plus de relecture, et aucune ligne de statut ne
   revient au bas de l'écran. Le kit de test ne sait pas lever `ui.close`, donc ce geste n'a jamais
   tourné.
